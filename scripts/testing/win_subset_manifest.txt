# ============================================================================
# CÓMO SE ELIGIÓ / HOW IT WAS PICKED — medido, no supuesto
# ============================================================================
# El filtro NO es un grep de builtins sobre el .nx (mide de más y de menos).
# Es la cadena real del job, reproducida en Linux antes de escribir esta
# lista, en tres pasos que cada candidato tiene que pasar:
#
#   1. COMPILA con NYX_TARGET=x86_64-pc-windows-msvc. El compilador ya rechaza
#      en codegen todo builtin de un subsistema no portado
#      (`win_forbidden_builtin`, compiler/codegen.nx) — red, threads/mutex/
#      goroutines, procesos, tls, señales, terminal — y también try/catch e
#      inline asm (codegen_target_guard). O sea: el gate de "no usa lo
#      prohibido" ya existe en el compilador; acá solo se COSECHA.
#   2. LINKEA contra EXACTAMENTE los 9 .o del subset (strings, runtime-arrays,
#      maps, time, iterators, sqlite_adapter, file-io, runtime, os_*). Un test
#      que toque un símbolo de un .c fuera del subset (url.c, persist.c, ...)
#      no linkea — y eso NO se ve en el .nx.
#   3. CORRE y su salida coincide con su expected/.
#
# Prioridad: tests CON expected/ (comparación fuerte). Los pocos sin expected/
# que entran son los que tienen assert() — assert aborta con exit 1, así que
# ahí "exit 0" SÍ es una aserción de verdad y no solo "no crasheó".
#
# EN: the filter is not a builtin grep — it is the job's real chain, replayed
# on Linux: (1) compiles under the windows triple (the compiler itself already
# rejects every not-ported subsystem via win_forbidden_builtin), (2) links
# against EXACTLY the subset's 9 objects (a symbol from a .c outside the
# subset is invisible in the .nx), (3) runs and matches its expected/.
# Tests with expected/ are preferred; the few without have assert(), which
# aborts with exit 1 — so there "exit 0" is a real assertion.
#
# ============================================================================
# EXCLUSIONES MEDIDAS / MEASURED EXCLUSIONS — el porqué de cada ausencia
# ============================================================================
# * THREADS (el canario de GC_beginthreadex que el brief pedía): IMPOSIBLE hoy.
#   `thread_spawn` está en win_forbidden_builtin (compiler/codegen.nx:3111,
#   `name.startsWith("thread_")`), así que test-90-thread-basic.nx ni siquiera
#   COMPILA para el triple windows: "error: 'thread_spawn' is not ported to
#   Windows yet". No es una elección de este manifiesto — es el gate de W0
#   todavía cerrado. El smoke del redirect de Boehm entra cuando W3 abra ese
#   builtin, junto con el resto del dominio de threads.
#   EN: the GC_beginthreadex canary is impossible today — thread_spawn is
#   still gated by win_forbidden_builtin, so the test does not even compile
#   for the windows triple. It arrives with W3, when that gate opens.
#
# * SQLITE (test-379-try-sqlite, test-162-sqlite, ...): fallarían, NO skipean.
#   Medido en runtime/sqlite_adapter.c:77-79 — la cadena de nombres del
#   dlopen lazy es SOLO Linux ("libsqlite3.so.0", "libsqlite3.so"). En
#   Windows LoadLibraryA de esos nombres falla → sqlite_load() marca
#   g_loaded=2 → nyx_sqlite_open devuelve NULL → try_sqlite_open da Err →
#   el test imprime "no-deberia" y DIFIERE de su expected/. Degrada, sí, pero
#   a una salida distinta, no a un skip. Agregar "sqlite3.dll" a esa cadena es
#   un cambio a sqlite_adapter.c (fuera del contrato de archivos de esta task)
#   y su lugar natural es W5, junto con los otros dos adapters (zlib, llama),
#   que tienen exactamente el mismo problema. sqlite_adapter.c SÍ se compila y
#   linkea en el job (está en la lista de TUs) — lo que no se ejercita es su
#   camino con biblioteca cargada.
#   EN: sqlite tests would FAIL, not skip: the lazy-dlopen name chain is
#   Linux-only, so on Windows the adapter degrades to "library missing" and
#   the test prints a different output than its expected/. Adding
#   "sqlite3.dll" belongs to W5 with the other two adapters.
#
# * test-133-web-framework: LINK-FAIL medido por un camino VIVO — llama
#   `parse_query_string` (std/web), que llama `url_decode`, que baja a
#   `nyx_url_decode` (runtime/url.c, fuera del subset). El test necesita url.c
#   de verdad: entra cuando url.c entre al subset.
# * test-339-wrap-next-closure: LINK-FAIL medido por ARRASTRE, no por uso —
#   sólo hace `import "std/web"` y nunca toca query strings; el import se
#   inlinea entero, así que `nyx_url_decode` termina referenciado igual. Es
#   deuda de granularidad del import (todo o nada), no una dependencia real
#   del test — si algún día el compilador emite sólo lo alcanzable, este entra
#   sin que url.c se mueva.
# EN: test-133 fails to link through a LIVE path (parse_query_string ->
# url_decode -> nyx_url_decode in url.c): it genuinely needs url.c. test-339
# fails by SPILLOVER: it only imports "std/web" and never touches query
# strings, but the import is inlined whole, so nyx_url_decode ends up
# referenced anyway — import granularity debt, not a real dependency.
# * test-295-chr-nul-safe: LINK-FAIL medido — `nyx_string_from_bytes` vive en
#   runtime/persist.c, que no está en el subset.
# * test-112-try-catch / test-335-try-catch-return-path: try/catch está
#   gateado para el triple windows (codegen_target_guard, no es residuo).
# * test-123-full-asm: inline asm, gateado igual.
# * test-144-sync: mutex_new → win_forbidden_builtin.
# * test-137-bench: su salida incluye tiempos — no determinista ni en Linux.
#
# ============================================================================

# El ÚNICO test del subset que toca el filesystem real de Windows (fopen/
# fwrite/fread/remove sobre la CRT de MSVC vía runtime/file-io.c).
#
# HALLAZGO de semántica win32 real, cazado por la iteración 1 de este job:
# el test escribe en rutas "/tmp/...", y una ruta que arranca con "/" NO es
# absoluta en Windows — resuelve a "raíz del DRIVE ACTUAL del proceso". El
# .exe es nativo, así que no ve el /tmp de Git Bash: ve la cadena literal. En
# el runner el workspace vive en D:\, así que crear C:\tmp no alcanzaba y el
# write daba ENOENT (code 2). El job ahora crea \tmp en el drive del workspace
# (ver windows.yml). Es setup de ENTORNO —el equivalente exacto de que /tmp
# exista en Linux—, no un parche: el test corre tal cual está commiteado.
# Consecuencia para el futuro: cualquier programa Nyx que hoy asuma que
# "/algo" es una ruta absoluta va a depender del drive en Windows. Es
# superficie de lenguaje, no de este job — ficha para el arco de paths (W5+).
# EN: the ONLY test here touching the real Windows filesystem. WIN32 FINDING
# from this job's iteration 1: it writes to "/tmp/..." paths, and a leading
# "/" is NOT absolute on Windows — it resolves to the root of the process's
# CURRENT DRIVE. The .exe is native, so it does not see Git Bash's /tmp. The
# runner's workspace is on D:, so creating C:\tmp was not enough and the write
# returned ENOENT (code 2). The job now creates \tmp on the workspace drive.
# Environment setup — exactly like /tmp existing on Linux — not a patch.
# Forward-looking: any Nyx program assuming "/x" is absolute becomes
# drive-dependent on Windows. Language surface, filed for the paths arc (W5+).
